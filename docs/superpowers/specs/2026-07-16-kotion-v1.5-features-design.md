# Kotion v1.5 Feature Set — Design

Date: 2026-07-16
Status: Approved (design), pending implementation plan

## Overview

Four independent, user-facing features added on top of the existing v1.4.1 codebase:

1. **Content search** — search inside page content, not just titles, with a matched-text snippet in results.
2. **Export** — export a page as a self-contained HTML file or as PDF (via the browser print dialog).
3. **Breadcrumb** — a clickable ancestor trail above the document title.
4. **Recent documents** — a "continue where you left off" section on the welcome screen.

Stack unchanged: Next.js 16 App Router, React 19, Tiptap 3.20, Prisma 7 + PostgreSQL, Zustand. No new runtime services and no new npm dependencies: `generateHTML` is imported from `@tiptap/core` (already installed) and export runs client-side using the browser DOM. The only build-time addition is Vitest (dev dependency) for unit tests.

Each feature is isolated and can be built and shipped independently; they share two small helpers (a Tiptap plain-text extractor and the editor extension list).

---

## Shared groundwork

### S1. Extract editor extension list into a shared module

Currently the Tiptap extension array is defined inline inside `useEditor(...)` in `src/components/editor/editor.tsx`. Export (HTML/PDF) and the plain-text extractor both need the same schema. 

Move the extension array into `src/components/editor/extensions/index.ts` as an exported factory `getEditorExtensions()` returning the configured extension array. `editor.tsx` imports and spreads it; export utilities import it to build a schema for `generateHTML`.

- Interface: `getEditorExtensions(): Extensions`
- Depends on: all existing extension imports (StarterKit, Table*, Columns, PageLink, CodeBlockLowlight, etc.).
- Constraint: must produce the SAME schema the live editor uses, so exported HTML matches on-screen rendering.

### S2. Tiptap plain-text extractor

`src/lib/tiptap-text.ts`, function `extractPlainText(doc: unknown): string`.

- Recursively walks a Tiptap JSON document.
- Collects `text` from text nodes.
- Inserts a newline between block-level nodes (paragraph, heading, listItem, tableRow, etc.) so the result reads naturally and snippets don't run words together.
- Returns a trimmed, single normalized string (collapse 3+ newlines to 2).
- Pure function, no dependencies, unit-testable in isolation.
- Used by: content-search indexing (server) and available for future needs.

## Feature 1: Content search

### Data model

Add to `Document` in `prisma/schema.prisma`:

```
contentText String?   // denormalized plain text of `content`, for search + snippets
```

No index in v1 (dataset is small, `ILIKE` scan is acceptable). Note in code that a `pg_trgm` GIN index on `contentText` is the future scaling path.

### Indexing (keeping contentText in sync)

`contentText` is derived from `content` whenever content changes:

- In `PATCH /api/documents/[documentId]` — when `content` is in the request body, compute `extractPlainText(content)` and include `contentText` in `updateData`.
- In `POST /api/documents` — when `content` is provided (template instantiation), also set `contentText`.

The extraction runs server-side using the shared `extractPlainText`. Keep it inside the same Prisma write (no extra round-trip).

### Backfill

One-off script `scripts/backfill-content-text.ts` (run via `tsx`): iterate all documents with non-null `content` and `contentText IS NULL`, compute and write `contentText`. Add an npm script `db:backfill-content-text`. Idempotent (only touches rows where `contentText` is null). Documented in the plan; run once after the migration.

### API

`GET /api/search?q=...` changes:

- Match on `title` OR `contentText`, `mode: insensitive`, `contains`.
- Scope: documents the user owns OR is a direct collaborator on (`collaborators: { some: { userId } }`). Archived excluded. (Inherited-through-parent access is out of scope for search v1.)
- For each result, compute a snippet server-side: find the first case-insensitive match of the query in `contentText` (fall back to title if match is only in title), take a window of ~150 chars centered on the match, trim to word boundaries, prefix/suffix with `…` when truncated.
- Response item: `{ id, title, icon, parentId, snippet: string | null, matchedIn: "title" | "content" }`.
- Limit 20, ordered by `updatedAt` desc.

### UI

`src/components/search-command.tsx`:

- Result row keeps icon + title, adds a second line with the snippet (muted, single line, truncated) when present.
- Highlight the matched query term inside the snippet (wrap matches in a `<mark>`-styled span). Highlight is computed on the client from the returned snippet + current query; escape to avoid HTML injection (snippet is plain text, rendered as text with highlight spans, never `dangerouslySetInnerHTML`).
- Existing keyboard nav, debounce, AbortController, and 401 handling (added in the recent audit) are preserved.

### Edge cases

- Empty/whitespace query → empty results (unchanged).
- Query matches only title → `snippet` null, `matchedIn: "title"`, row shows title only.
- `contentText` null (not yet backfilled) → treated as no content match; title still searchable.
- Very long contentText → snippet window bounds the returned size; full text never sent to client.

### Files

- `prisma/schema.prisma` (add field)
- `src/lib/tiptap-text.ts` (new, S2)
- `src/app/api/documents/route.ts` (POST sets contentText)
- `src/app/api/documents/[documentId]/route.ts` (PATCH sets contentText)
- `src/app/api/search/route.ts` (content match + snippet + shared scope)
- `src/components/search-command.tsx` (snippet + highlight)
- `scripts/backfill-content-text.ts` (new), `package.json` (script)

## Feature 2: Export (HTML + PDF)

Both are fully client-side. Triggered from a new "Dışa Aktar" (Export) menu in the toolbar.

### Shared: rendered HTML

`src/lib/export.ts`:

- `documentToHTML(doc: { title, icon, coverImage, content }): string` — uses `generateHTML` (imported from `@tiptap/core`) with `getEditorExtensions()` for the body, wraps it in a full HTML document with:
  - `<title>` = page title, `<meta charset>`, viewport.
  - An inline `<style>` block containing the editor content styles needed for faithful rendering (headings, lists, task lists, tables with borders/alignment, code blocks, columns, images, page-link blocks, blockquote, highlight). This CSS is a self-contained subset extracted/adapted from `globals.css` editor styles, kept in the export module so the file renders identically standalone.
  - Page title heading (and cover image if present) at the top.
- Images: content references app-internal `/api/files/...` URLs (auth-protected). For a truly portable file, `documentToHTML` (or the caller) resolves each image to a `data:` URI by fetching it with credentials and base64-encoding, before serialization. If a fetch fails, fall back to leaving the original URL (best-effort). This runs client-side where the session cookie is available.

### HTML export

`exportAsHTML(doc)`: build the HTML string (with data-URI images), create a `Blob`, trigger a download named `<slugified-title>.html`.

### PDF export

`exportAsPDF(doc)`: render the same HTML into a hidden `<iframe>` (or a new window), call `iframe.contentWindow.print()`, which opens the browser's print dialog where the user chooses "Save as PDF". Clean up the iframe after printing. Print-oriented CSS (`@page` margins, avoid breaking inside tables/code blocks where possible) is included in the export stylesheet under `@media print`.

### UI

- Toolbar (`src/components/toolbar.tsx`): add an "Export" button/menu next to (or near) the Share button. Menu with two items: "HTML olarak indir", "PDF olarak kaydet". In-app dropdown consistent with existing menus (no browser dialogs). Available to any role that can view the document (owner, editor, viewer) — exporting is read-only.
- Pass the current document (title, icon, coverImage, content) from the document page into the toolbar (already available there).

### Edge cases

- Empty document → exports an empty (but valid) HTML/PDF with just the title.
- Large images / many images → data-URI inlining may be slow; show a brief loading state on the menu item while building.
- Image fetch fails (e.g. deleted file) → keep original URL, don't block the export.
- Popup blockers (PDF via new window) → use a hidden same-document iframe instead of `window.open` to avoid blockers.

### Files

- `src/components/editor/extensions/index.ts` (new, S1)
- `src/components/editor/editor.tsx` (use shared extensions)
- `src/lib/export.ts` (new)
- `src/components/toolbar.tsx` (export menu)
- `src/app/(main)/documents/[documentId]/page.tsx` (pass content to toolbar if not already)

## Feature 3: Breadcrumb

### Data

Extend `GET /api/documents/[documentId]` response with an `ancestors` array: the parent chain from root down to (but not including) the current document, each as `{ id, title, icon }`. Built server-side by walking `parentId` up (bounded depth, same pattern as the existing access-check walk), then reversed to root-first. Only ancestors the user can access are included (they already have access to the current doc, and access is inherited, so the full chain is safe to show).

### UI

`src/components/breadcrumb.tsx` (new), rendered in the document page above the toolbar/title:

- `Notlar › [ancestor] › … › [current title]`.
- "Notlar" links to `/documents`. Each ancestor links to `/documents/<id>`. Current page is plain text (not a link).
- Each item shows its icon (small) + title, truncated.
- If the chain (ancestors + current) exceeds 4 items, collapse the middle into `…` (show root, `…`, last ancestor, current).
- Root-level documents show just `Notlar › [current title]`.
- Reflects the `ancestors` array from the document fetch; ancestors refetch on navigation. (No live title-override wiring in v1 — a renamed ancestor updates on next navigation, which is acceptable.)

### Edge cases

- Document with no parent → `Notlar › current`.
- Deep chain → middle-ellipsis.
- Ancestor deleted between load and click → navigation lands on a 404-guarded page that redirects to `/documents` (existing behavior).

### Files

- `src/lib/document-access.ts` or `src/app/api/documents/[documentId]/route.ts` (build ancestors)
- `src/components/breadcrumb.tsx` (new)
- `src/app/(main)/documents/[documentId]/page.tsx` (render breadcrumb, consume ancestors)

## Feature 4: Recent documents

### API

Add `recent=true` support to `GET /api/documents` (or a dedicated branch): return the N (=6) most recently updated documents accessible to the user (owned + direct collaborations), non-archived, ordered by `updatedAt` desc, selecting `{ id, title, icon, updatedAt, parentId }`.

### UI

Welcome page (`src/app/(main)/documents/page.tsx`), above the templates section:

- Section "Kaldığın yerden devam et" with up to 6 cards.
- Each card: icon + title + relative time ("2 saat önce"), links to `/documents/<id>`.
- Hidden entirely when the user has no documents.
- Relative-time helper `src/lib/format-relative-time.ts`, Turkish output ("az önce", "5 dakika önce", "3 saat önce", "dün", "2 gün önce", or absolute date beyond ~7 days). Pure, unit-testable.

### Edge cases

- No documents → section not rendered.
- Fewer than 6 → show what exists.
- Fetch failure → section hidden, welcome page still works (templates remain).

### Files

- `src/app/api/documents/route.ts` (recent branch)
- `src/lib/format-relative-time.ts` (new)
- `src/app/(main)/documents/page.tsx` (recent section)

## Testing

No test infrastructure exists yet. Add lightweight **Vitest** setup and unit tests for the pure helpers, which carry the most logic risk:

- `extractPlainText` — nested nodes, tables, empty docs, block separation.
- snippet builder — match at start/middle/end, no match, truncation boundaries.
- `formatRelativeTime` — boundaries (just now, minutes, hours, days, older).

API/route and UI behavior verified manually against the running dev server (as in the recent audit), plus `tsc` and a production build.

## Rollout / migration notes

- `contentText` is nullable, so the Prisma change is additive and safe (`db push` won't drop data). Run the backfill script once after applying the schema change.
- No new long-running services; Docker image unchanged except the possible `@tiptap/html` dependency.
- All four features degrade gracefully if their data is missing (null contentText, no ancestors, no recent docs).

## Out of scope (v1.5)

- Full-text ranking / `pg_trgm` index (documented future path).
- Search across inherited-through-parent shared access (only direct owner/collaborator scope).
- Server-side PDF rendering (Puppeteer) — using browser print instead.
- Export formats other than HTML/PDF (e.g. Markdown, DOCX).
- Breadcrumb drag-to-reparent or editing from the trail.
