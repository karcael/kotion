# Database Documentation

This document describes the Kotion database schema: every model, field, enum,
relation, and index defined in [`prisma/schema.prisma`](./prisma/schema.prisma),
plus how the application uses each of them. It is meant to be accurate to the
schema as written - if the schema changes, this file should be updated in the
same change.

## 1. Overview

| Component | Detail |
|---|---|
| Database engine | PostgreSQL 17 (`postgres:17-alpine` in `docker-compose.yml`) |
| ORM | Prisma ORM 7.5.x (`prisma`, `@prisma/client`, `@prisma/adapter-pg`, all pinned to `^7.5.0`) |
| Driver adapter | [`@prisma/adapter-pg`](https://www.npmjs.com/package/@prisma/adapter-pg) (`PrismaPg`), wrapping `node-postgres` (`pg`) |
| Schema file | `prisma/schema.prisma` |
| Config file | `prisma.config.ts` (project root) |

**Client setup.** `src/lib/prisma.ts` builds the singleton `PrismaClient` with an
explicit driver adapter instead of Prisma's bundled query engine binary:

```ts
const adapter = new PrismaPg({ connectionString: process.env.DATABASE_URL! })
return new PrismaClient({ adapter })
```

No `previewFeatures` flag is needed for this in the installed Prisma version -
driver adapters are stable. Because the app talks to Postgres through `pg`
directly, the production Docker image copies `pg` and its transitive
dependencies (`pg-pool`, `pg-protocol`, `pg-connection-string`, etc.) alongside
the generated Prisma client instead of relying on a Rust query-engine binary
(see `Dockerfile`).

**Two independent places resolve `DATABASE_URL`:**

1. **Prisma CLI** (`db push`, `db studio`, `generate`) reads it through
   `prisma.config.ts`, which imports `dotenv/config` to load `.env` and only
   attaches a `datasource.url` when `DATABASE_URL` is actually set - there is
   no fallback URL, so a missing variable fails loudly instead of silently
   pointing at the wrong database:

   ```ts
   const databaseUrl = process.env.DATABASE_URL
   export default defineConfig({
     schema: path.join(__dirname, "prisma", "schema.prisma"),
     ...(databaseUrl ? { datasource: { url: databaseUrl } } : {}),
   })
   ```

   This is a Prisma 7 requirement: the config file lives at the project root
   (not next to `schema.prisma`), and Prisma 7 no longer reads `.env`
   automatically once a config file is present - hence the explicit
   `dotenv/config` import.

2. **The running Next.js app** reads `process.env.DATABASE_URL` directly in
   `src/lib/prisma.ts` when constructing the `PrismaPg` adapter, independent of
   `prisma.config.ts`. In Docker, `DATABASE_URL` is injected as a real
   environment variable (`docker-compose.yml`); in local dev, Next.js loads
   `.env` itself.

Note that `datasource db { provider = "postgresql" }` in `schema.prisma`
intentionally has **no `url = env(...)` line** - the connection string is
never hard-coded into the schema file itself; it is only ever supplied at
runtime by one of the two paths above.

**Connection string format** (`.env.example`):

```
DATABASE_URL="postgresql://kotion:kotion@localhost:5432/kotion"
```

**Table names** match the Prisma model names verbatim (`User`, `Document`,
`Invitation`, `Collaborator`) - no `@@map` directives are used anywhere in the
schema.

**npm scripts:**

| Script | Command | Purpose |
|---|---|---|
| `npm run db:push` | `prisma db push` | Syncs the database schema to match `prisma/schema.prisma` without generating a migration file. This is the only schema-sync mechanism currently used (see [Migrations](#6-migrations)). |
| `npm run db:studio` | `prisma studio` | Opens Prisma Studio, a local GUI for browsing and editing rows. |
| `npm run db:backfill-content-text` | `tsx scripts/backfill-content-text.ts` | One-off maintenance script (see [`Document.contentText`](#22-document)) that fills in `contentText` for any `Document` rows that have JSON `content` but no plain-text copy yet - e.g. rows created before the column existed. It only selects `contentText: null` rows, so re-running it after a successful run is a no-op. |

## 2. Models

### 2.1 User

Represents an account. Authentication is handled elsewhere (JWT + bcrypt, see
`src/lib/auth.ts`); this table only stores the account record itself.

| Field | Type | Attributes | Default | Description |
|---|---|---|---|---|
| `id` | `String` | `@id` | `cuid()` | Primary key, a collision-resistant ID generated by Prisma at insert time. |
| `name` | `String` | required | - | Display name, shown in the sidebar, collaborator lists, and invitation emails. |
| `email` | `String` | `@unique` | - | Login identifier. Also used to match invitations sent to an address before the invitee had (or had linked) an account. |
| `password` | `String` | required | - | bcrypt password hash. Plaintext passwords are never stored. |
| `image` | `String?` | optional | `null` | URL/path to the user's avatar image. |
| `createdAt` | `DateTime` | required | `now()` | Row creation timestamp. |
| `updatedAt` | `DateTime` | `@updatedAt` | auto-managed | Automatically set by Prisma to the current time on every update to the row. |

**Relations** (not columns on `User` - see [section 4](#4-relations-and-cascade-behavior)):

| Field | Type | Related model | Description |
|---|---|---|---|
| `documents` | `Document[]` | `Document` | Documents owned by this user (inverse of `Document.user`). |
| `sentInvitations` | `Invitation[]` | `Invitation` (`SentInvitations`) | Invitations this user has sent as the inviter. |
| `receivedInvitations` | `Invitation[]` | `Invitation` (`ReceivedInvitations`) | Invitations linked to this user's account as the invitee. |
| `collaborations` | `Collaborator[]` | `Collaborator` | Documents this user has Editor/Viewer access to as a non-owner. |

### 2.2 Document

The core content entity - a single page. Pages can be nested to form a tree via
`parentId`/`children`.

| Field | Type | Attributes | Default | Description |
|---|---|---|---|---|
| `id` | `String` | `@id` | `cuid()` | Primary key. |
| `title` | `String` | required | `"Adsız"` (Turkish for "Untitled") | Page title, shown in the sidebar, browser tab, breadcrumbs, and search results. |
| `content` | `Json?` | optional | `null` | The page body as Tiptap/ProseMirror JSON - the editor's native document format. |
| `contentText` | `String?` | optional | `null` | **v1.5 addition.** A denormalized, plain-text copy of `content`. See below. |
| `icon` | `String?` | optional | `null` | Page icon. Stores one of: a raw emoji character, a `lucide:<IconName>:<color>` encoded string for colored Lucide icons (e.g. `lucide:Star:yellow`), or an uploaded image path/URL. Dispatched by prefix in `src/components/page-icon.tsx`. |
| `coverImage` | `String?` | optional | `null` | URL/path to the cover image banner shown above the title. |
| `isArchived` | `Boolean` | required | `false` | Soft-delete ("Trash") flag. `true` means the page has been moved to Trash. |
| `isFavorite` | `Boolean` | required | `false` | Whether the owner has starred this page for the sidebar "Favorites" section. |
| `isPublished` | `Boolean` | required | `false` | Whether the page is published for public read-only access. Owner-only to toggle (enforced in the `PATCH` route). |
| `position` | `Int` | required | `0` | Manual sort order among sibling documents (same `parentId`). Rewritten in bulk by `PATCH /api/documents/reorder` when the user drags a page to a new position in the sidebar. |
| `parentId` | `String?` | optional (FK) | `null` | The parent page's `id`, or `null` for a root-level page. |
| `userId` | `String` | required (FK) | - | The owning user's `id`. Every document has exactly one owner, independent of its parent's owner - a collaborator can create a sub-page they own themselves underneath a page owned by someone else. |
| `createdAt` | `DateTime` | required | `now()` | Row creation timestamp. |
| `updatedAt` | `DateTime` | `@updatedAt` | auto-managed | Bumped on every update, including autosave. |

**`contentText` in detail:** it exists purely to make search fast and simple
without parsing Tiptap JSON on every request. It is produced by
`extractPlainText()` (`src/lib/tiptap-text.ts`), which walks the Tiptap JSON
tree, concatenates text nodes, and separates block-level nodes (paragraphs,
headings, list items, table rows, etc.) with newlines. It is written on every
content-bearing write path:

- `POST /api/documents` - sets it at creation time, if `content` is supplied.
- `PATCH /api/documents/[documentId]` - recomputes it whenever `content` is
  present in the request body.

It is then read by `GET /api/search`, which does a case-insensitive
`contains` match against `contentText` (alongside `title`) and builds result
snippets from it.

**There is no database trigger or generated column involved** - synchronization
is entirely application-maintained. Any write path that updates `content`
without also setting `contentText` (e.g. a manual `prisma.document.update` in
a script or in Prisma Studio) will leave it stale; `npm run db:backfill-content-text`
exists to (re)populate it for rows where it is `null`.

**Relations:**

| Field | Type | Related model | Cascade | Description |
|---|---|---|---|---|
| `parent` | `Document?` | `Document` (self, `"ParentChild"`) | `onDelete: SetNull` | The parent page, or `null` for root pages. |
| `children` | `Document[]` | `Document` (self, `"ParentChild"`) | - (inverse side) | Direct child pages. |
| `user` | `User` | `User` | `onDelete: Cascade` | Owning user. |
| `invitations` | `Invitation[]` | `Invitation` | - (inverse side) | Share invitations issued for this document. |
| `collaborators` | `Collaborator[]` | `Collaborator` | - (inverse side) | Users with current Editor/Viewer access to this document. |

See [section 4](#4-relations-and-cascade-behavior) for what these cascade
rules actually do (and, for delete/archive/restore, do *not* do) to a page's
subtree.

**Indexes:** `@@index([userId])`, `@@index([parentId])`,
`@@index([userId, isArchived])` - see [section 5](#5-indexes).

### 2.3 Invitation

A share invite sent to an email address, granting a role on a document once
accepted.

| Field | Type | Attributes | Default | Description |
|---|---|---|---|---|
| `id` | `String` | `@id` | `cuid()` | Primary key. |
| `email` | `String` | required | - | The address the invitation was sent to. Normalized to lowercase by the API before insert. Does not require the address to already have an account (see `inviteeId`). |
| `role` | `CollaboratorRole` | required | `EDITOR` | Access level to grant if/when accepted. |
| `status` | `InvitationStatus` | required | `PENDING` | Current lifecycle state. |
| `documentId` | `String` | required (FK) | - | The document being shared. |
| `inviterId` | `String` | required (FK) | - | The user who sent the invitation. |
| `inviteeId` | `String?` | optional (FK) | `null` | The user account tied to this invitation. Set at creation time if an account with a matching email already exists; otherwise `null` until the invitee acts on it. Also (re-)set to the acting user's `id` when the invitation is accepted or declined via `PATCH /api/invitations/[invitationId]`, regardless of its prior value. |
| `createdAt` | `DateTime` | required | `now()` | Row creation timestamp. |
| `updatedAt` | `DateTime` | `@updatedAt` | auto-managed | Bumped whenever the invitation is re-sent (status reset to `PENDING`) or resolved (accepted/declined). |

**Relations:**

| Field | Type | Related model | Cascade | Description |
|---|---|---|---|---|
| `document` | `Document` | `Document` | `onDelete: Cascade` | The shared document. |
| `inviter` | `User` | `User` (`"SentInvitations"`) | `onDelete: Cascade` | The sender. |
| `invitee` | `User?` | `User` (`"ReceivedInvitations"`) | `onDelete: Cascade` | The linked recipient account, if any. |

**Application behavior worth noting:** accepting an invitation
(`status: "ACCEPTED"`) does not by itself grant access - the API route
additionally `upsert`s a matching `Collaborator` row (`documentId` + `userId`,
with the invitation's `role`) in the same request. Declining leaves the
`Invitation` row in place as a record; no `Collaborator` row is created.
Canceling a still-pending invitation (`DELETE`) removes the row entirely.

**Indexes:** `@@unique([documentId, email])`, `@@index([email, status])`,
`@@index([inviteeId, status])` - see [section 5](#5-indexes).

### 2.4 Collaborator

A resolved grant of access: user X has role Y on document Z. Created when an
invitation is accepted (or re-accepted).

| Field | Type | Attributes | Default | Description |
|---|---|---|---|---|
| `id` | `String` | `@id` | `cuid()` | Primary key. |
| `role` | `CollaboratorRole` | required | `EDITOR` | Access level: `EDITOR` or `VIEWER`. The document's actual owner is never represented as a `Collaborator` row - see the [`CollaboratorRole` enum note](#32-collaboratorrole). |
| `documentId` | `String` | required (FK) | - | The document being accessed. |
| `userId` | `String` | required (FK) | - | The user granted access. |
| `createdAt` | `DateTime` | required | `now()` | Row creation timestamp. |

Note: unlike the other three models, `Collaborator` has **no `updatedAt`
field** - a role change (e.g. re-accepting an invitation with a different
role) updates `role` in place without recording when that happened.

**Relations:**

| Field | Type | Related model | Cascade | Description |
|---|---|---|---|---|
| `document` | `Document` | `Document` | `onDelete: Cascade` | The shared document. |
| `user` | `User` | `User` | `onDelete: Cascade` | The collaborating user. |

**Indexes:** `@@unique([documentId, userId])`, `@@index([userId])` - see
[section 5](#5-indexes).

## 3. Enums

### 3.1 InvitationStatus

```prisma
enum InvitationStatus {
  PENDING
  ACCEPTED
  DECLINED
}
```

| Value | Meaning |
|---|---|
| `PENDING` | Default state. Sent, awaiting the invitee's response. Re-sending an existing pending-or-resolved invitation to the same document/email resets it back to `PENDING`. |
| `ACCEPTED` | Invitee accepted. A `Collaborator` row is upserted alongside this status change (application logic, not a DB effect). |
| `DECLINED` | Invitee explicitly declined. The row is kept as a record; no `Collaborator` row is created. |

### 3.2 CollaboratorRole

```prisma
enum CollaboratorRole {
  VIEWER
  EDITOR
}
```

| Value | Meaning |
|---|---|
| `VIEWER` | Read-only access. Cannot edit content (`PATCH` on a document is rejected for this role) or create sub-pages under the document. |
| `EDITOR` | Read/write access to content, but not to owner-only actions (archive, favorite-toggle-as-non-owner is fine, publish, delete - see the `ownerOnlyFields` check in `PATCH /api/documents/[documentId]`). |

**Note:** there is no `OWNER` value in this enum. Ownership is never stored as
a `CollaboratorRole` - it is derived at request time in
`src/lib/document-access.ts` by checking whether `Document.userId === userId`.
The `DocumentRole` type used throughout the app (`"OWNER" | "EDITOR" | "VIEWER"`)
is a superset of this enum for that reason: `OWNER` is implicit, the other two
values come directly from the database.

## 4. Relations and Cascade Behavior

| Relation | `onDelete` | Effect of deleting the "one" side |
|---|---|---|
| `Document.parent` → `Document` (self, `"ParentChild"`) | `SetNull` | Deleting a document sets `parentId = NULL` on its direct children instead of deleting them. Children become root-level pages rather than disappearing. |
| `Document.user` → `User` | `Cascade` | Deleting a user deletes every `Document` row they own outright. (No account-deletion endpoint exists in the app today; this rule would only fire via a direct database operation or a future admin feature.) |
| `Invitation.document` → `Document` | `Cascade` | Deleting a document deletes all invitations tied to it. |
| `Invitation.inviter` → `User` | `Cascade` | Deleting a user deletes invitations they sent. |
| `Invitation.invitee` → `User` | `Cascade` | Deleting a user deletes invitations linked to their account as recipient. |
| `Collaborator.document` → `Document` | `Cascade` | Deleting a document deletes all collaborator grants on it. |
| `Collaborator.user` → `User` | `Cascade` | Deleting a user deletes all their collaborator grants on other documents. |

**Important: the `Document` self-relation is deliberately `SetNull`, not
`Cascade`.** A raw `DELETE` on a single document row never takes its
descendant subtree with it at the database level. Because a document's
`userId` is independent of its parent's `userId` (a collaborator can own a
sub-page nested under someone else's page), a blanket cascade on the
self-relation would risk deleting pages across ownership boundaries that the
deleting user doesn't necessarily own.

**Recursive archive / restore / delete is entirely application logic**, not a
database cascade. It lives in
`src/app/api/documents/[documentId]/route.ts`:

- **Delete** (`DELETE`, owner-only): `collectDescendantIds()` walks the tree
  breadth-first, one query per depth level (`findMany({ where: { parentId: { in: frontier } } })`),
  bounded to 100 levels to guard against cycles, then the whole subtree is
  removed in a single `document.deleteMany({ where: { id: { in: [documentId, ...descendantIds] } } })`.
- **Archive** (`PATCH` with `isArchived: true`): the same descendant-collection
  walk runs inside a `prisma.$transaction`, setting `isArchived: true` on every
  descendant via `updateMany` alongside the `update` on the target document
  itself, so a page and its whole subtree move to Trash atomically.
- **Restore** (`PATCH` with `isArchived: false`): `collectArchivedAncestorIds()`
  walks *up* the parent chain (also bounded to 100 levels) collecting any
  archived ancestors, then restores them together with the target document in
  one transaction - restoring a nested page also un-archives the chain of
  parents needed to reach it.

Because `isArchived` is a plain boolean column with no relation to cascade
behavior, none of the archive/restore semantics come from the schema itself -
they are fully reconstructed in application code every time.

## 5. Indexes

Beyond the indexes Postgres creates implicitly for `@id` primary keys and
`@unique`/`@@unique` constraints (`User.email`, `Invitation.[documentId, email]`,
`Collaborator.[documentId, userId]`), the schema defines these explicit
indexes:

| Model | Index | Query it serves |
|---|---|---|
| `Document` | `@@index([userId])` | Listing a user's own documents - the base filter of nearly every `GET /api/documents` variant (root pages, favorites, archived, "all pages" for the page-link picker). |
| `Document` | `@@index([parentId])` | Fetching a page's direct children - sidebar tree expansion, and the breadth-first `collectDescendantIds()` walk used by delete/archive. |
| `Document` | `@@index([userId, isArchived])` | The composite filter used by the main sidebar list and the Trash view: `where: { userId, isArchived }`. A single composite index serves both columns together instead of intersecting two separate single-column indexes. |
| `Invitation` | `@@unique([documentId, email])` | Enforces at most one invitation row per document/email pair; also the lookup used to find an existing invitation before creating or re-sending one (`POST /api/invitations`). |
| `Invitation` | `@@index([email, status])` | The `email = ? AND status = 'PENDING'` branch of the "my pending invitations" query (`GET /api/invitations`, and the accept/decline lookup in `PATCH /api/invitations/[invitationId]`), which matches by either `inviteeId` or `email`. |
| `Invitation` | `@@index([inviteeId, status])` | The `inviteeId = ? AND status = 'PENDING'` branch of that same query. |
| `Collaborator` | `@@unique([documentId, userId])` | Enforces one collaborator row per user per document; also the point lookup used on every access check in `src/lib/document-access.ts` (direct access, and again per ancestor while walking up the parent chain) and the accept-invitation upsert. |
| `Collaborator` | `@@index([userId])` | Listing all documents a user collaborates on - `getSharedDocuments()` / the "Shared with me" sidebar section. |

**Search is not index-backed.** `GET /api/search` filters on
`title` and `contentText` with a case-insensitive `contains` (`ILIKE '%...%'`),
and neither column has a dedicated index (no `pg_trgm`/GIN index, no
`tsvector` column). This is a plain sequential scan over each user's
accessible documents, acceptable at small/self-hosted scale; it would be the
first thing to revisit if search latency becomes a problem on a larger corpus.

## 6. Migrations

There is currently no Prisma Migrate history in this project. Schema changes
are applied with `prisma db push` (`npm run db:push`), which diffs
`prisma/schema.prisma` against the live database and applies the difference
directly, without generating a `migrations/` folder or a record of individual
schema changes over time.

The production `Dockerfile` runs the same command on every container start,
**without** `--accept-data-loss`:

```
prisma db push --schema=./prisma/schema.prisma --url $DATABASE_URL && node server.js
```

This means a schema change that Prisma considers destructive (e.g. dropping a
column, narrowing a type) will stop the container from starting rather than
silently applying it - a deliberate safety net for a self-hosted app where
nobody is watching a migration diff before every deploy.

`.gitignore` no longer excludes a `prisma/migrations/` directory, which means
the project is set up to move to `prisma migrate` (with a committed migration
history) whenever that becomes worth the added process - at that point, the
first migration would need to be baselined against whatever schema is already
live in existing self-hosted instances.
